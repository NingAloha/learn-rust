### 生命周期省略

您已经了解到每个引用都有一个生命周期，并且需要为使用引用的函数或结构体指定生命周期参数。然而，在“理解所有权”的“Slices”一节中的“使用字符串切片改进 `first_word` 函数的 `s` 参数类型”中，我们提供了一个不带生命周期标注却可以编译的函数，如下所示：

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return &s[0..i];
        }
    }

    &s[..]
}
```

#### 我们在“Slices”中定义的一个不需要生命周期标注的函数，即便参数和返回类型是引用

这个函数可以不带生命周期标注编译的原因是历史因素：在早期版本（1.0之前）的Rust中，这段代码无法编译，因为每个引用都需要一个显式生命周期。那时，函数签名应该写成这样：

```rust,ignore
fn first_word<'a>(s: &'a str) -> &'a str {
```

在编写了大量Rust代码后，Rust团队发现程序员在特定情况下反复输入相同的生命周期标注。这些情况是可预测的，并遵循一些确定性模式。开发人员将这些模式编入编译器的代码中，因此借用检查器可以在这些情况下推断生命周期，而不需要显式标注。

这一段Rust历史很重要，因为未来可能会出现更多确定性模式并被添加到编译器中。将来，可能需要的生命周期标注会更少。

Rust对引用分析编程的模式称为*生命周期省略规则*。这些不是程序员需要遵循的规则，而是一组编译器会考虑的特定情况，如果您的代码符合这些情况，就不需要明确写出生命周期。

省略规则并没有提供完整推断。如果Rust决定性地应用规则但仍然存在关于引用应有的生命周期的歧义，编译器不会猜测剩余引用的生命周期应该是什么。此时，编译器会给出一个错误，您可以通过添加说明引用之间关系的生命周期标注来解决。

函数或方法参数上的生命周期称为*输入生命周期*，返回值上的生命周期称为*输出生命周期*。

当没有显式标注时，编译器使用三个规则来确定引用的生命周期。第一个规则适用于输入生命周期，第二和第三个规则适用于输出生命周期。编译器在使用这三个规则后如果仍然有无法确定生命周期的引用，编译器将以错误告终。这些规则适用于`fn`定义以及`impl`块。

第一个规则是每个作为引用的参数获得其自己的生命周期参数。换句话说，一个参数的函数得到一个生命周期参数：`fn foo<'a>(x: &'a i32)`；两个参数的函数得到两个单独的生命周期参数：`fn foo<'a, 'b>(x: &'a i32, y: &'b i32)`；依此类推。

第二个规则是如果只有一个输入生命周期参数，该生命周期将分配给所有输出生命周期参数：`fn foo<'a>(x: &'a i32) -> &'a i32`。

第三个规则是如果有多个输入生命周期参数，但其中一个是`&self`或`&mut self`，因为这是一个方法，`self`的生命周期将分配给所有输出生命周期参数。这个第三个规则使得方法更易于阅读和编写，因为需要的符号更少。

让我们假装我们是编译器。我们将应用这些规则来确定`first_word`函数签名中引用的生命周期。签名一开始没有与引用相关联的生命周期：

```rust,ignore
fn first_word(s: &str) -> &str {
```

然后编译器应用第一个规则，它规定每个参数得到其自己的生命周期。我们像往常一样称之为`'a`，所以现在签名是这样的：

```rust,ignore
fn first_word<'a>(s: &'a str) -> &str {
```

第二个规则适用，因为只有一个输入生命周期。第二个规则规定一个输入参数的生命周期分配给输出生命周期，所以现有的签名是这样的：

```rust,ignore
fn first_word<'a>(s: &'a str) -> &'a str {
```

现在，这个函数签名中的所有引用都有生命周期，编译器可以继续分析，而不需要程序员在这个函数签名中标注生命周期。

让我们看看另一个例子，这次使用`longest`函数，当我们在第10-21节开始时处理它时没有生命周期参数：

```rust,ignore
fn longest(x: &str, y: &str) -> &str {
```

让我们应用第一个规则：每个参数获得其自己的生命周期。这次我们有两个参数，而不是一个，所以我们有两个生命周期：

```rust,ignore
fn longest<'a, 'b>(x: &'a str, y: &'b str) -> &str {
```

您可以看到第二个规则不适用，因为有多个输入生命周期。第三个规则也不适用，因为`longest`是一个函数而不是方法，所以没有参数是`self`。在处理完所有三个规则后，我们仍然没有确定返回类型的生命周期。这就是我们在尝试首次实现`longest`函数时编译代码时遇到错误的原因：编译器处理了生命周期省略规则，但仍然无法确定签名中引用的所有生命周期。

因为第三个规则实际上只适用于方法签名，我们将接下来在该上下文中查看生命周期，看看为什么第三个规则意味着我们不必经常在方法签名中标注生命周期。
