### 单元测试

单元测试的目的是在与其他代码隔离的情况下测试每个代码单元，以快速定位代码是否按预期工作。您应将单元测试放在 *src* 目录中，与它们正在测试的代码文件一起。惯例是为每个文件创建一个名为 `tests` 的模块来容纳测试函数，并用 `cfg(test)` 注解模块。

#### 测试模块和 `#[cfg(test)]`

在测试模块上的 `#[cfg(test)]` 注解告诉 Rust 仅在您运行 `cargo test` 时编译和运行测试代码，而不是在您运行 `cargo build` 时。这在您只想构建库时节省了编译时间，并在结果编译成品中节省了空间，因为测试不被包含。由于集成测试放在不同的目录中，所以它们不需要 `#[cfg(test)]` 注解。然而，因为单元测试与代码在同一文件中，所以您需要使用 `#[cfg(test)]` 指定它们不应包含在编译结果中。

回忆本章第一个部分中由 cargo new 自动生成的测试模块和函数的示例：

```rust
#[cfg(test)]
mod tests {
    #[test]
    fn it_works() {
        assert_eq!(2 + 2, 4);
    }
}
```

这段代码是自动生成的测试模块。属性 `cfg` 代表*配置*，告诉 Rust 后续的项目应仅在特定配置选项下才被包含。在本例中，配置选项是 `test`，它是 Rust 用于编译和运行测试时提供的。通过使用 `cfg` 属性，Cargo 仅在我们主动用 `cargo test` 运行测试时编译我们的测试代码。这包括可能在此模块中存在的任何帮助函数，以及标注有 `#[test]` 的函数。

#### 测试私有函数

在测试社区中是否应直接测试私有函数这一点上存在争议，其他语言则让测试私有函数变得困难或不可能。无论您遵循哪种测试理念，Rust 的隐私规则确实允许您测试私有函数。请考虑下面带有私有函数 `internal_adder` 的代码。

```rust
pub fn add_two(a: i32) -> i32 {
    internal_adder(a, 2)
}

fn internal_adder(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn internal() {
        assert_eq!(4, internal_adder(2, 2));
    }
}
```

##### 测试私有函数

请注意，`internal_adder` 函数没有被标记为 `pub`，但因为测试也只是 Rust 代码，而 `tests` 模块只是另一个模块，您可以将 `internal_adder` 引入到测试的作用域并调用它。如果您不认为私有函数应被测试，Rust 中没有什么会迫使您这样做。
